# PIPELINE — как выполняется задача

Один процесс для любого агента. Правила — `AGENTS.md`, текст задачи и «Готово, когда» — `docs/BACKLOG.md` (при расхождении с Jira прав он). Где шаг различается по агентам, действуй по колонке своего агента.

Человек пишет только команду и отвечает на остановки; ветку, тесты, коммиты, PR, ревьюера и статусы Jira ведёт агент.

## Запуск

| Команда | Что делает агент |
|---|---|
| `/setup` | настраивает окружение — раздел «Настройка» |
| `/task` | берёт следующую задачу из очереди пользователя в `docs/TEAM.md` и выполняет её |
| `/task AH-7` | выполняет задачу AH-7 (шаги 0–10) |
| `/task Ревью AH-7` | проверяет PR задачи и после «да» мержит его — раздел «Ревью и мерж» |

| Агент | Правила | Как вызвать | Особенности |
|---|---|---|---|
| Claude Code | `CLAUDE.md` → `AGENTS.md` | `/task …`, `/setup` | `/task` — не из plan mode: шаг 0 переключает ветку |
| Codex | `AGENTS.md` | `$task …`, `$setup` | личные заметки — в `~/.codex/AGENTS.md`, не в `AGENTS.override.md` |
| Gemini CLI | `GEMINI.md` → `AGENTS.md` | `/task …`, `/setup` из корня репозитория | после правки команды — `/commands reload` |

Остановки (ждать ответа человека): после плана и перед push; в режиме ревью — перед мержем. Других остановок нет, кроме случаев из раздела «Если шаг невозможен».

## Jira

Проект `KAN` на `alphaimpact2.atlassian.net`, через MCP Atlassian. Задача ищется по `project = KAN AND summary ~ "AH-<n>"`; accountId пользователя — из MCP (информация о текущем пользователе). Статусы и id переходов: «К выполнению» 11, «В работе» 21, «В процессе проверки» 31, «Готово» 41. Инструментов MCP Atlassian нет — остановиться и сказать: «запустите `/setup`».

## Шаг 0 — задача и ветка

1. Найти ключ `AH-<n>` в запросе. Ключа нет и запрос не пустой — задать один вопрос: завести ли задачу в `docs/BACKLOG.md`. Запрос пустой — взять следующую задачу:
   - кто пользователь — `gh api user -q .login` и колонка GitHub в `docs/TEAM.md`;
   - его очередь — таблица участника в `docs/TEAM.md`, по порядку;
   - первая задача, которая в Jira не «Готово» и не «В процессе проверки», а все её «Зависит от» смержены (п. 3); задачи с несмерженными зависимостями пропускаются. Объявить, какая задача взята.
2. Прочитать блок задачи (эпик, день, тип, «Зависит от», «Что сделать», «Готово, когда») и документы, на которые он ссылается.
3. «Зависит от»: `git fetch origin`, затем для каждого ключа `git log origin/dev --oneline -E --grep "AH-<k>([^0-9]|$)"` — непустой вывод значит, что PR задачи смержен (поиск идёт по всему сообщению коммита, `AH-1` не путается с `AH-12`). Пусто — сказать и спросить, продолжать ли.
4. Тип — из поля «Тип:». Противоречит описанию — один вопрос. Объявить одной строкой: ключ, тип, ветка.
5. Рабочее дерево грязное — остановиться и спросить.
6. Есть открытый PR задачи (`gh pr list --search "AH-<n> in:title" --state open`) — это доработка после ревью: `gh pr checkout <номер>`, прочитать замечания (`gh pr view <номер> --comments`), план (шаг 1) — по замечаниям. Иначе `git switch dev && git pull && git switch -c <ветка>`.
7. Jira: назначить задачу на пользователя и перевести в «В работе».

## Типы задач

| Тип | Ветка | Шаг 2 |
|---|---|---|
| feat | `feat/AH-<n>-<slug>` | тесты на новое поведение (RED), затем код (GREEN) |
| fix | `fix/AH-<n>-<slug>` | падающий регрессионный тест, затем исправление |
| изменение поведения | `feat/` или `fix/` по смыслу | обновить существующие тесты под новую спецификацию, затем код |
| refactor | `refactor/AH-<n>-<slug>` | без новых тестов; зелёно до и после |
| contract | `feat/AH-<n>-contract-<slug>` | контрактный тест → `shared/contracts` → все реализации → `docs/CONTRACTS.md` |
| test | `test/AH-<n>-<slug>` | тесты и тестовая обвязка; продакшн-код — только исправления, названные в задаче, каждое после упавшего теста; показать, что каждый новый тест может упасть |
| docs / chore | `docs/AH-<n>-<slug>`, `chore/AH-<n>-<slug>` | без TDD; план, коммит и проверка обязательны |

- slug — английский kebab-case, 2–4 слова.
- TDD обязателен для сервисов, `shared/` и логики фронта (хуки, состояние, API-клиент). Для чистой JSX-вёрстки шаг 2 — render-тест Vitest и зелёный `npm run build`.
- Тесты, которые фиксируют заглушку этой задачи (`NotImplementedError("AH-<n>")`, ответ 501), переписываются под настоящее поведение.

Шаг 10 после «да»:
1. `git push -u origin <ветка>`.
2. Новый PR: `gh pr create --base dev --title "AH-<n> · <название>" --reviewer <GitHub ревьюера>`; ревьюер — по колонке «Ревьюит» в `docs/TEAM.md`. Описание: что сделано / как проверить («Готово, когда» чек-листом и список ручной проверки) / риски. Доработка после ревью — PR уже есть: `gh pr comment <номер> --body "Замечания исправлены: …"`.
3. Jira: «В процессе проверки» и комментарий со ссылкой на PR.
4. Последней строкой ответа: «Ревьюер: <имя> — `/task Ревью AH-<n>`».

Коммиты — по правилам `AGENTS.md`.

## Ревью и мерж — `/task Ревью AH-<n>`

1. Найти открытый PR: `gh pr list --search "AH-<n> in:title" --state open`. Нет — сказать и остановиться. Автор PR — сам пользователь (`gh pr view <номер> --json author`) — сказать, что свой PR одобрить нельзя, назвать ревьюера из `docs/TEAM.md` и остановиться.
2. Рабочее дерево грязное — остановиться и спросить. Иначе `gh pr checkout <номер>`.
3. `gh pr checks <номер>` — CI зелёный; раздел «Проверка» целиком; чек-лист ревью (в Claude Code — `/code-review` без флагов); сверка с «Готово, когда» задачи в `docs/BACKLOG.md`.
4. **Стоп:** показать итог (что проверено, замечания, список ручной проверки из описания PR) и спросить: «Мержить?»
5. «Да»:
   - `gh pr review <номер> --approve`, затем `gh pr merge <номер> --merge --delete-branch`;
   - `git switch dev && git pull`, `git branch -d <ветка PR>`;
   - Jira: «Готово».
6. Замечания: `gh pr review <номер> --request-changes --body "<замечания списком>"`; Jira: «В работе»; сказать: «Автору — `/task AH-<n>`». Затем `git switch dev`.

## Настройка — `/setup`

Один раз на машине; повторный запуск безопасен. Каждый пункт — проверить, а чинить только то, что не так. В конце — таблица: пункт / готово / что сделать пользователю.

1. Инструменты: `git`, `docker`, `uv`, `node` (мажорная версия 22, как в CI), `gh`. Чего-то нет — показать список и после «да» поставить: Windows — `winget install --id <id>` для нужных из `Git.Git`, `Docker.DockerDesktop`, `astral-sh.uv`, `OpenJS.NodeJS.22`, `GitHub.cli`, затем перезапустить агента, чтобы обновился PATH; Linux — пакетный менеджер дистрибутива. Docker Desktop требует WSL2 (`wsl --install`) и может попросить перезагрузку — сказать об этом.
2. `gh auth status`. Не вошёл — попросить пользователя выполнить `gh auth login` (в Claude Code — `! gh auth login`, в остальных агентах — в отдельном терминале). `git config user.name` и `user.email` пусты — спросить и задать.
3. Нет `.env` в корне — `cp .env.example .env`. `LLM_API_KEY` пуст — попросить пользователя вписать ключ в `.env` самому (ключ не передаётся через чат).
4. `cd backend && uv sync`, `cd frontend && npm ci`.
5. `docker info` не отвечает — на Windows запустить Docker Desktop (`cmd //c start "" "C:\Program Files\Docker\Docker\Docker Desktop.exe"`) и ждать `docker info` до 2 минут. Затем `docker compose up -d --build --wait` и `docker compose --profile seed run --rm seed`; `http://localhost:8000/health` и `http://localhost:5173` отвечают 200.
6. Jira: инструменты MCP Atlassian доступны и поиск `project = KAN AND summary ~ "AH-49"` находит задачу. Иначе дать пользователю команду для своего агента, сервер `https://mcp.atlassian.com/v1/mcp`, вход через браузер учётной записью Jira, затем перезапуск агента:
   - Claude Code: `claude mcp add --transport http --scope user atlassian https://mcp.atlassian.com/v1/mcp`, затем `/mcp` → atlassian → вход (или коннектор Atlassian в настройках claude.ai);
   - Codex: `codex mcp add atlassian --url https://mcp.atlassian.com/v1/mcp`, затем `codex mcp login atlassian`;
   - Gemini CLI: `gemini mcp add --transport http --scope user atlassian https://mcp.atlassian.com/v1/mcp`, затем `/mcp auth atlassian`.
7. `backend/data/raw` пуст — сказать: файлы кейса (три csv и отчёты банка) нужны только для задач с данными, их даёт Участник 2.
8. Кто пользователь: `gh api user -q .login` → строка в `docs/TEAM.md`. Нет в таблице — сказать. Есть — показать его очередь на сегодня и закончить строкой: «Дальше: `/task`».

## Проверка

Из корня репозитория, Docker запущен, в корне есть `.env` (один раз: `cp .env.example .env`). Каждая команда должна пройти:

```
docker compose --profile test up -d --wait db_test
cd backend
uv run ruff check .
uv run ruff format --check .
uv run mypy --strict shared
uv run mypy apps main.py scripts tests
uv run lint-imports
uv run --env-file ../.env pytest
cd ../frontend
npm run gen:types
git diff --exit-code -- app-plugin/src/types
npm test
npm run build
```

Если `git diff` что-то показал — сгенерированные типы разошлись со схемами: закоммитить их вместе с изменением контракта.

## Чек-лист чистки (шаг 4)

- Нет кода, не нужного для одобренного плана
- Нет дублирования между сервисами; общее — только через `shared`
- Файлы ≤ 500 строк, функции делают одно
- Нет комментариев и закомментированного кода
- Нет дефолтов и фолбэков, не одобренных явно
- Имена говорят сами; магические числа — в настройки

## Чек-лист ревью (шаг 8 и режим ревью)

- Сервис импортирует только разрешённое в `AGENTS.md` (`uv run lint-imports` зелёный)
- Контракт не изменён или изменён задачей типа contract
- Каждый `Claim` имеет `source_ref`; `CounterpartyContext` без чужих идентификаторов; `silent` обработан в UI
- Новая зависимость → строка в `THIRD_PARTY_NOTICES.md`; lock-файл обновлён
- LLM вызывается только через `apps/services/llm`
- Нет секретов в коде; требования раздела «Безопасность» в `docs/ARCHITECTURE.md` выполнены (в Claude Code — ещё `/security-review`)
- Тесты проверяют поведение, а не реализацию; нет тестов, которые всегда зелёные
- README и `docs/` не разошлись с кодом

## Если шаг невозможен

- Нет инструмента или падает окружение — остановиться и сказать, что именно; не обходить. Похоже на ненастроенную машину — предложить `/setup`.
- У агента нет встроенной команды для шага — выполнить шаг по чек-листу.
- Проверка падает в чужом коде — не чинить в своей ветке; сказать пользователю, а после исправления у владельца подтянуть `dev`: `git pull origin dev`.
- Задаче нужна правка контракта, а её тип не contract — остановиться и сказать.
