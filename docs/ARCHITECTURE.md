# ARCHITECTURE

Монолит на Python с изолированными сервисами внутри: один процесс, один `main.py`, один DI-контейнер, но каждый сервис живёт в своём пакете, знает только свои таблицы и общается с остальными исключительно через контракты из `shared/contracts`.

## Правила изоляции

Сами правила — в `AGENTS.md`, раздел «Service isolation»; здесь — как они устроены.

- Зависимость между сервисами выражается портом из `shared/contracts/ports.py` и разрешается из DI-контейнера. Пример: `interpreter` получает `ProfileService`, `CounterpartyService`, `NewsService`, `HouseViewService`, `WhatIfService`, `ProductRulesService`, `LLMGateway`, `TraceStore` в конструктор.
- Сервис экспортирует только `register(container: Container) -> None`. Сервис — пакет в `apps/services/`: `main.py` находит его сам и вызывает `register` с контейнером, где уже есть `Settings`, `AsyncEngine` и `async_sessionmaker`; общие файлы при добавлении сервиса не правятся.
- Проверка — `tests/unit/test_import_boundaries.py` запускает `import-linter` с контрактами из `backend/pyproject.toml`: `independence` между `apps.services.*`, `forbidden` на `shared.db.migrations`, `layers` — `shared` не зависит от сервисов.

## Поток запроса

```
контейнер (application / extension) → POST /interpret {user_id, client_id, role, action_context}
gateway: auth → права → нормализация → ключ кэша (user, client, role, type, hash(context), profile_version, house_view_version) → попадание? ответ
interpreter.interpret():
  1 prefilter (без LLM): кандидаты-новости по отрасли/региону контрагента или факторам клиента, утверждения house view по теме; пусто → silent
  2 plan: шаблон по типу действия + дополнение моделью; план в трассу
  3 tools: вызовы портов, единый объект контекста
  4 draft: InsightCard по шести блокам, каждый тезис {text, type, source_ref}
  5 critic: источники / bank-тезисы из house view / противоречия / «не пересказ»; до 2 кругов
  6 trace.save(); gateway кэширует (кроме ответа с `needs_review`, AH-60); ответ
```

AH-18 реализует шаги до черновика: профиль читается с проверкой доступа, для платежа запрашиваются агрегаты получателя, затем выполняется предфильтр AH-15. Пустой отбор даёт `silent: true` без вызова LLM. В `interpreter/plans.yaml` заданы шаблоны для `payment`, `deposit`, `fx`, `loan`, `payroll`, `dashboard` и `page`, окно 14 дней, выборка 200 новостей и максимум 4 дополнительных вызова. `page` (живая новость, AH-40): первая непустая строка текста — заголовок, остальное — тело; строка длиннее `max_title_chars` (`plans.yaml`) обрезается в заголовок, а весь текст идёт телом; `NewsService.annotate` возвращает новость из индекса или размечает и сохраняет её; предфильтр оценивает только эту новость тем же счётом и порогом, без окна дат, ниже порога — `silent: true`; текст страницы не повторяется в `action` промпта (он уже в источнике `news:<id>`); пустой текст — доменная ошибка. `followup` описан ниже (AH-26).

AH-19 подключает этот поток к HTTP. Сессия — cookie `alfa_session` с id пользователя из `POST /auth/mock` (только прототип); без cookie или с неизвестным пользователем — 401. Права user → client и версию профиля gateway берёт одним вызовом `ProfileService.get_profile`: чужой `client_id` и `user_id` в теле, не совпадающий с сессией, — 403, проверка идёт до кэша. Ключ кэша — sha256 от пользователя, клиента, роли, типа действия, sha256 канонического JSON контекста, `ClientProfile.version` (растёт при каждой правке профиля) и `HouseViewService.version()`; обе версии читаются на каждый запрос. Кэш не общий между пользователями одного клиента: ответ из кэша несёт `trace_id` собственного прошлого запроса пользователя. Ответы хранятся в `interpret_cache` (Postgres, срок `CACHE_TTL_SECONDS`, просроченные удаляются при записи); кэшируется любой успешный ответ, включая `silent`, ошибки — нет; исключение — ответ, где хотя бы одна карточка с `needs_review` (непроверенная карточка после второго круга критика или после сбоя критика, переписывания, исчерпания бюджета — AH-22): он в кэш не пишется, и повторный запрос снова идёт в interpreter (AH-60); попадание отдаёт ответ с `cached: true` без вызова interpreter. Каждый авторизованный `/interpret` пишется в `gateway_calls`: пользователь, клиент, тип действия, хэш контекста (не сам текст), `trace_id` первой карточки, попадание в кэш, итог (`ok` или класс ошибки), длительность; модель и токены — в трассе. Сбои записи в кэш и в журнал пишутся в лог: ответ отдаётся (итог в журнале — `ok`), ошибка interpreter не подменяется. Доменные ошибки переводятся в HTTP: `AccessDenied` — 403, `NotFound` — 404, `BudgetExceeded` — 503, прочий `DomainError` — 422.

План и черновик — два структурированных вызова `LLMGateway.complete(task="interpret")`. Модель уточняет акцент шаблона и запрашивает только `HouseViewService.claims` по известным факторам или `chain` по уже полученным актуальным утверждениям. Весь план проверяется до выполнения; неизвестные операции, аргументы, повторы и превышение лимита отклоняются. Результаты вызовов объединяются с профилем, агрегатами и кандидатами в единый контекст; в черновик попадают только актуальные `approved`-утверждения. Идентификаторы пользователя, клиента, группы и получателя, ИНН и сырые строки CSV в промпты не передаются.

Модель возвращает пять блоков тезисов с ключами источников. Interpreter разрешает ключи через собранный реестр `SourceRef` и собирает шестой блок `basis` из использованных ссылок. Неизвестный источник отклоняется; `bank` дословно цитирует текущее утверждение house view, прогноз и выведенный признак нельзя обозначить фактом. Отсутствие позиции банка оставляет `bank_view` пустым. Это структурная проверка черновика; карточка пока без продуктового предложения и расчётов whatif.

Критик AH-22 — `interpreter/critic.py`, порт `Critic`: `review` получает карточку, актуальные `approved`-утверждения из контекста и отобранные новости и возвращает список нарушений `<код>: <деталь>`; пустой список — карточка принята. Коды: `source` — источник тезиса не из переданных новостей и house view, пустой id или ссылка не в `basis`; `bank` — тезис `bank` не цитирует дословно актуальное (`approved`, без `superseded_by`) утверждение или в `bank_view` тезис другого типа; `contradiction` — тезис `fact`/`ai` противоречит утверждению house view и не начинается со слова «Расхождение» (ведущие пробелы, кавычки и тире пропускаются, «Расхождением» — не пометка); `retelling` — меньше двух различных источников или ни одного признака компании (`profile`) или агрегата получателя (`graph`). Противоречия ищет отдельный вызов `LLMGateway.complete(task="critic")` со своим промптом: модель получает только пронумерованные тезисы без пометки и утверждения house view и отвечает номерами тезисов; учитываются только выданные номера и известные id, текст вердикта берётся из карточки, повторы сводятся в один вердикт; без house view модель не вызывается. Цикл: черновик → круг 1; есть нарушения — черновик переписывается с прошлым черновиком и замечаниями, круг 2; нарушения после второго круга — `needs_review: true`, иначе `false`. Каждый круг — шаг трассы `critic` (`round N`, список нарушений), в `Trace.critic_verdicts` — `N: ok` или `N: <нарушение>`. Токены вызова критика в шаг не попадают (порт возвращает только вердикты), расход учитывается в `llm_usage`. Доменная ошибка или ответ не по схеме после сборки первой карточки (критик, переписывание, сборка переписанного черновика, второй круг — в том числе `BudgetExceeded`) запрос не роняет: отдаётся последняя собранная карточка с `needs_review: true`, в `critic_verdicts` — `N: error: <класс ошибки>`, как требует правило бюджета в разделе LLM-шлюза ниже. Прочие исключения трассируются и передаются вызывающему.

В `TraceStore.save` передаётся трасса с шаблоном и дополнением плана, вызовами портов, временем, моделью, токенами и результатом; ошибки также трассируются и передаются вызывающему без запасной модели или ответа. Ошибка записи трассы не подавляется. Шаг инструмента хранит аргумент и JSON результата, шаг `plan` — JSON шаблона и плана, шаги `draft` и `redraft` — JSON черновика; все усечены до `trace_summary_chars` из `plans.yaml`. В тестах AH-18 хранилище трасс и LLM заменены моками; интеграционный сквозной тест использует настоящие профиль, граф, индекс и house view через DI и PostgreSQL. HTTP-маршрут `POST /interpret` подключается в AH-19.

Followup (AH-26): вопрос к карточке приходит в `/interpret` с `FollowupContext`. Вопрос без текста или длиннее `max_question_chars` (`plans.yaml`) — доменная ошибка до создания трассы: недопустимый ввод в трассу не попадает; в трассу и промпт идёт вопрос без пробелов по краям. Interpreter берёт исходную трассу через `TraceStore.find_by_card` (пользователя и клиента сверяет хранилище: `NotFound` / `AccessDenied` до чтения профиля и вызова модели); если карточка сама — ответ на followup, по той же цепочке `find_by_card` доходит до исходного запроса (не глубже `max_followup_depth` звеньев из `plans.yaml`, иначе доменная ошибка до чтения профиля и вызова модели с текстом для пользователя: диалог длиннее N вопросов, задайте вопрос к исходной карточке), и в `action` промпта идёт действие исходной карточки (депозит, платёж) с текущей ролью. Затем заново читает профиль своей компании, для исходного платежа — агрегаты получателя через `CounterpartyService.context` (источники `graph:*` фактические, как в основном сценарии), и по очереди для каждого утверждения house view из `basis` карточки вызывает `HouseViewService.chain`: в контекст попадают только актуальные `approved`-утверждения, устаревшее заменяется преемником и как текущее не цитируется. Утверждение, которого больше нет среди подтверждённых (`chain` даёт `NotFound`), пропускается: в трассе шаг `house_view.chain` с `NotFound`, у ответа нет позиции банка по нему. Новости берутся из `basis` исходной карточки без повторного поиска: значение источника — заголовок, url, дата и тексты тезисов типа `fact`, которые на неё ссылаются (тексты `ai`-тезисов в источник не попадают); новость без `fact`-тезисов остаётся в источниках с заголовком, url и датой, но нефактической и как `fact` не цитируется (`sources` помечает нефактической любую новость с пустым текстом); новость без заголовка, url или даты публикации не предлагается; критик получает новости, собранные из этих ссылок (id, заголовок, url, дата). План модели (`followup_focus` в `plans.yaml`) добавляет `house_view.claims` и `house_view.chain` только при необходимости, с той же проверкой, что и основной сценарий; при достаточном контексте `tools=[]`. План и черновик — задача `followup` шлюза (`MODEL_FOLLOWUP`, без рассуждений); промпт получает вопрос, исходную карточку с ключами источников, признаки и источники, без идентификаторов пользователя, клиента, карточки и получателя. Ответ — карточка с новым `id` в новой трассе через тот же черновик, сборку и круги критика, поэтому пометки `fact` / `bank` / `ai` и источники сохраняются; в трассе каждый шаг `trace.find_by_card` хранит только id найденной трассы; шаги трассы идут в порядке начала вызова.

Сервис `trace` (AH-23) хранит трассу целиком в `traces.payload` (JSONB). `TraceStore.feedback` находит трассу карточки запросом `payload @> {"result": {"cards": [{"id": card_id}]}}` по GIN-индексу `jsonb_path_ops` и пишет в `feedback` upsert по уникальному `card_id`: повторный отзыв заменяет прежний. `TraceStore.metrics(since)` читает трассы с `created_at` от начала дня `since` (UTC) и считает: `sourced_claims_share` — доля тезисов карточек с непустым `source_ref.id`; `critic_first_pass_share` — доля трасс с кругом критика, где первый круг дал `1: ok`; `silent_share` — доля `silent` среди трасс с результатом; `tokens_per_card` — токены всех шагов трасс с карточками на одну карточку (без токенов критика); `cache_share` — доля успешных LLM-шагов (с `model` и JSON-результатом; упавший шаг хранит имя ошибки) с нулём токенов, то есть попаданий в кэш LLM (ответы из кэша `/interpret` трассы не создают). Показатель без данных за период в ответ не входит. Маршруты шлюза требуют сессию: `GET /trace/{id}` — 404 для неизвестной трассы и 403 для чужой; `GET /metrics?since=YYYY-MM-DD` — `since` обязателен; `POST /feedback` — 204, чужая карточка — 403, неизвестная — 404.

Предфильтр AH-15 — `backend/apps/services/interpreter/prefilter.py`, внутренняя часть сервиса для подключения в AH-18. `Prefilter` получает порты `NewsService`, `HouseViewService` и `threshold=Settings.RELEVANCE_THRESHOLD`; `select` принимает профиль, действие, агрегаты контрагента (или `None`) и явные `since`, `as_of`, `limit`. Результат — кандидаты с оценками и актуальные `approved`-утверждения по факторам отобранных новостей. Ошибки портов передаются вызывающему коду.

Оценка — скалярное произведение силы факторов из общего словаря и экспозиций плюс 1 за каждое из четырёх измерений с точным совпадением в `NewsItem.entities`: отрасль, регион, страна, продукт. Повтор фактора учитывается по максимальной силе; направление не меняет значимость, так как экспозиция описывает чувствительность. `shared/config/news_entities.py` задаёт общую нормализацию и ключи `industry:logistics`, `region:москва`, `country:китай`, `company:…`, `product:loan`: пробелы схлопываются, регистр убирается, подстроки, синонимы и совпадения между разными типами не учитываются. Для платежа отрасль и регион берутся только из контекста контрагента, для остальных действий — из профиля. Страны — `import_countries` и страна валютного действия; продукты — `products` и продукт действия для кредита, депозита, зарплаты. Пустые признаки не дают совпадений. Кандидаты с оценкой не ниже порога сортируются по убыванию оценки, затем по `id`.

Порт поиска не принимает продукт и набор стран: предфильтр запрашивает новости без фильтров факторов и сущностей, с `since` и явным положительным `limit`. В этом режиме индекс выбирает последние новости, ограничивая их число в SQL и не читая векторы; при равной дате порядок по `id`. Затем предфильтр отбирает локально, исключая будущие новости относительно `as_of`. Ранжирование относится только к полученной выборке, полнота за её пределами не гарантируется. Интеграционный тест с PostgreSQL строит профиль и граф из CSV, разрешает настоящие сервисы через DI и проверяет отбор и время < 200 мс для 200 записей вместе с чтением индекса и house view. Данные синтетические, house view — подтверждённый seed; API-подключение — AH-18. Генератор и команды проверки — в README.

Разметка новостей выдаёт продукты из общего словаря (`settlement`, `guarantee`, `loan`, `leasing`, `deposit`, `payroll`, `factoring`) с подсказками `product_hints` в `news/config.yaml`; неизвестный продукт и ответ без списка продуктов отклоняются. Новые схема и промпт меняют ключ кэша LLM. Исторические записи автоматически не переразмечаются и сохраняют прежние сущности; совпадение по продукту требует тега `product:…`.

## Пакетный контур

`scripts.seed` запускает по порядку: пользователи → загрузка csv → чистка → профили и агрегаты графа; ключ LLM ему не нужен. Новости собирает отдельная команда `scripts.ingest_news` (`docker compose --profile seed run --build --rm -e LLM_TIMEOUT_SECONDS=30 seed python -m scripts.ingest_news` — при 8 с часть ответов прокси не успевает, а таймаут оставляет в `llm_usage` резерв), ей нужен ключ LLM: ленты из `NEWS_RSS_URLS` → новости за `max_age_days` → отсев уже известных (хэш заголовка, адрес) → эмбеддинг e5 → дубль, если у одной из `dedup_candidates` ближайших новостей за ±`dedup_window_hours` косинус ≥ `dedup_threshold` и те же числа и месяцы (повторы числа не считаются) → разметка Gemma: регион и код страны — только из справочника `shared/config/geography.py`, Россия — не регион и не страна → `news` (`apps/services/news/config.yaml`). Недоступная лента и ошибка модели или эмбеддинга на новости не останавливают прогон, исчерпанный бюджет останавливает; повторный запуск размечает только новые новости. После смены промпта или справочника индекс переразмечает `scripts.reannotate_news` (`docker compose --profile seed run --build --rm --no-deps -e LLM_TIMEOUT_SECONDS=30 seed python -m scripts.reannotate_news`): заново размечает каждую новость и обновляет `entities` и `factors`, ошибка на новости оставляет старую разметку. `NewsService.search` берёт новости с `since` по пересечению факторов или по отрасли, региону и стране (регион и страна — по справочнику из любого их написания: «Татарстан» и «Республика Татарстан», «ОАЭ» и «ae»; места вне справочника нет и в индексе) и ранжирует по сумме силы совпавших факторов плюс число совпавших полей; `annotate` (AH-40) обрезает текст до `max_text_chars`, ищет вставку по её id (хэш `manual:` + заголовок + текст — пространство id отдельно от лент) и новость из ленты по адресу, затем по правилу дубля (эмбеддинг и те же числа за ±`dedup_window_hours` от текущего времени): найденную новость из ленты возвращает без вызова модели, а у похожей вставки берёт только разметку и пишет новую строку со своим текстом; иначе размечает текст и пишет его в индекс с `source = manual` и текущим временем, а если запись проиграла параллельной вставке — возвращает сохранённую. Вставка всегда пишется под адресом `manual:<id>`, адрес пользователя только ищется среди лент. Вставки — недоверенный текст одного пользователя: `search` их не отдаёт, сбор лент не считает их дублями и не путает с ними свои id и адреса, а текст одной вставки не попадает в ответ на другую. OCR отчётов банка и извлечение утверждений — отдельная команда `scripts.ingest_reports` (`docker compose --profile seed run --rm -e LLM_TIMEOUT_SECONDS=120 seed python -m scripts.ingest_reports` — пакетному извлечению нужен таймаут больше интерактивного): ей нужны tesseract (есть в образе backend) и ключ LLM; страницы распознаются один раз (кэш по хэшу картинки в `report_pages`), утверждения пишутся черновиками `draft` в `house_view_claims` (отчёт по стали — `expired`), подтверждение — в `data/seed/house_view_approved.json` (AH-14). Повторный запуск идемпотентен.

## Модели и бюджет

| Задача | Модель |
|---|---|
| Разметка новостей и текста страниц | Gemma 4 26B A4B |
| Извлечение утверждений из отчётов | Qwen3.6 35B A3B |
| План и черновик карточки | GLM-5.3-Flash (запасной Qwen3.6) |
| Критик | GLM-5.3-Flash, другой промпт |
| Уточняющий вопрос | Qwen3.6 35B A3B |
| Эмбеддинги: дубли и индекс новостей | multilingual-e5-small локально (ONNX, префикс `query: `), не тратит бюджет |

Для `extract` и `followup` шлюз отключает рассуждения через `reasoning_off_tasks` в `apps/services/llm/models.yaml`: запрос содержит `reasoning: {enabled: false}`, этот режим входит в ключ кэша. `followup` остаётся на Qwen3.6 с общим интерактивным таймаутом `LLM_TIMEOUT_SECONDS=8`; рассуждения остальных задач не отключаются (AH-56).

Онлайн- и пакетные вызовы тратят общий дневной пул `LLM_DAILY_BUDGET_RUB × (1 − LLM_BUDGET_RESERVE_SHARE)`; 10% — резерв, не тратится; деление на онлайн и пакет пока не делается. Перед вызовом модели шлюз под advisory-блокировкой Postgres проверяет остаток и резервирует `LLM_CALL_RESERVE_RUB` строкой в `llm_usage`, после ответа резерв заменяется фактическим расходом — стоимостью из ответа прокси (`usage.cost`, рубли; ею же прокси списывает лимит ключа) — или снимается; параллельные вызовы api и seed не проходят лимит вместе. `models.yaml` — только allow-list моделей, цен в нём нет: прокси их не публикует. Эмбеддинги считает локальная модель (`embedder.json`, файлы — в `backend/models`, скачиваются при сборке образа): без HTTP, без резерва и без строк в `llm_usage`. Кэш ответов и эмбеддингов живёт `LLM_CACHE_TTL_SECONDS`, просроченные записи удаляются при записи в кэш. При исчерпании шлюз поднимает `BudgetExceeded`, ответы из кэша отдаются и дальше, вызывающий отвечает `needs_review`. Ошибки шлюза — `BudgetExceeded`, `ModelUnavailable` (HTTP-ошибка, таймаут, обрыв соединения или битое тело ответа 200 — не JSON, нет `choices` / `usage`, `content` не строка, счётчик токенов не целое ≥ 0 или в `usage` нет `cost`; расход записывается по `usage.cost`, если он есть, при `usage` без корректного конечного `cost` и при таймауте (прокси мог списать вызов) в `llm_usage` остаётся резерв; для `embed` — нет файлов локальной модели), `ModelOutputInvalid` (пустой ответ или не по схеме), `UsageNotRecorded` (ответ получен и закэширован, но расход не записан — в `llm_usage` остаётся резерв), `CacheNotWritten` (ответ получен и расход записан фактом, но запись в кэш не удалась; для `embed` — вектор посчитан, но не закэширован) — подклассы `DomainError`. Длина вектора не равна `EMBEDDING_DIMENSION` — `EmbeddingDimensionMismatch` (`ValueError`, ошибка конфигурации, а не `DomainError`).

## Безопасность

- Инструменты проверяют права; `counterparty_context` отдаёт только агрегаты (тест `tests/integration/test_counterparty_no_leak.py`).
- В промпты — признаки и агрегаты; персональные данные физлиц в модель не попадают.
- Журнал вызовов: `user_id`, `client_id`, `trace_id`, модель, токены, время.
- Расширение: токен со скоупом `interpret:read`, короткий TTL; на сервер уходит текст страницы и ИНН, журнал хранит хэш текста.
- Текст страницы — недоверенные данные: инструкции внутри игнорируются, критик требует источники из базы.
