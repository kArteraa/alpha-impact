# MANUAL_CHECKS — ручные проверки всех задач

Здесь собрано то, что автотесты не покрывают: вид экранов, демо, качество текста карточек, живая модель. Источник — раздел «Как проверить» в PR каждой задачи; новые проверки дописывает шаг 8 `docs/PIPELINE.md`. Проверки сгруппированы по экранам: идите по разделам сверху вниз. У каждой проверки: шаги, «Ожидается» и «Плохо, если» — признаки, по которым проверка не пройдена.

Результат пишется в сводную таблицу: кто, дата, ✅ или ❌ с коротким описанием. Непройденная проверка — строка риска в своём файле `docs/decisions/` или новая задача в `docs/BACKLOG.md`.

Владельцы: Участник 1 — Михаил (`kArteraa`), Участник 2 — Дмитрий (`Atr1a`), Участник 3 — Артём (`Zerrant2`).

## Подготовка

Один раз перед проверками, из корня репозитория, на свежем `dev` (или на ветке PR, если проверяется PR):

```bash
docker compose up -d --build --wait
docker compose --profile seed run --build --rm seed
```

- В `.env` — ключ LLM (`LLM_API_KEY`), в `backend/data/raw` — три csv и PDF отчётов банка (их даёт Участник 2).
- Приложение — `http://localhost:5173`, API — `http://localhost:8000`, Swagger — `http://localhost:8000/docs`.
- Тестовые пользователи (`backend/data/seed/users.json`): `user_cfo_wholesale` — оптовик `U_1941` и «СтройЛизинг» `U_9250`; `user_cfo_autodealer` — автодилер `U_44245`; `user_cfo_construction` — стройгруппа `U_9250`; `user_cfo_nocard` — клиент без карточек `U_235754`.
- Роль выбирается на `/role` после входа.
- Запросы к API без UI: в Swagger выполнить `POST /auth/mock` с `{"user_id": "<пользователь>"}` — cookie сессии ставится на `localhost:8000`, дальше `POST /interpret`, `GET /trace/{id}`, `GET /metrics` работают из того же окна.
- `trace_id` карточек регрессии — таблица в разделе «Регрессия» README. Трассу открывает только её пользователь: `/trace/<trace_id>` под пользователем кейса.
- Каждый вызов модели стоит денег (бюджет ≈ 500 ₽ в день); повтор того же запроса отвечает из кэша шлюза бесплатно.

## Вход и профиль

### MC-01 · Вход, роль и подтверждение профиля
Подготовка: стек и seed. Шаги:
1. `http://localhost:5173` → войти за `user_cfo_wholesale`.
2. Выбрать роль «Финдиректор».
3. Экран профиля: поправить одно поле, нажать «Всё верно».

Ожидается: после входа — выбор роли, затем профиль оптовика (отрасль, импорт из Китая и Турции, кредиты и лизинг, компании группы); правка сохраняется, «Всё верно» ведёт на главный экран; вид интернет-банка без чужого брендинга, заголовок вкладки «Альфа-Бизнес · Alpha Impact».

Плохо, если: правка пропадает после перезагрузки; при сбое сохранения нет сообщения об ошибке; «Всё верно» не ведёт на главную; на экране видны идентификаторы `U_*` других компаний.

### MC-02 · Правка отрасли пересчитывает экспозиции
Подготовка: стек и seed. Шаги:
1. В Swagger `POST /auth/mock` за `user_cfo_construction`, `GET /profile/U_9250` — записать экспозиции.
2. `PATCH /profile/U_9250/features/industry_class` со значением `energy`, снова `GET /profile/U_9250`.
3. Повторить seed (`docker compose --profile seed run --rm seed`) и снова `GET /profile/U_9250`.

Ожидается: после правки экспозиции другие; после повторного seed правка пользователя на месте, `version` не меняется при повторном seed без правок.

Плохо, если: экспозиции не изменились; seed затёр правку пользователя.

Плохо, если: «Не успел собрать события» (таймаут модели — смотреть трассу ленты); списки двух компаний совпадают; после смены компании фокус клавиатуры теряется и не возвращается в шапку.

## Платёж

### MC-04 · Платёж перевозчику: карточка с агрегатами получателя
Подготовка: вход `user_cfo_wholesale`, роль «Финдиректор». Шаги:
1. «Платёж» (`/payments/new`), получатель «Северо-Западная логистика» (`U_96105`), сумма 1 500 000.
2. Дождаться карточки рядом с формой.

Ожидается: карточка по шести блокам; в «почему важно» — доля логистики в оттоке клиента (около 43%) и отрасль получателя; позиция банка — логистика и склады по отчёту банка; у каждого тезиса пометка «Факт / Банк / AI» и источник; есть действие (например, аккредитив).

Плохо, если: в карточке ИНН, суммы или продукты получателя (разрешены только отрасль, регион, размер, доля, уверенность); тезис без источника; карточка про сам платёж без новости в основании.

### MC-05 · Явное молчание: компания без карточки
С AH-46 и AH-65 молчание показывает не платёж «Канцмиру» (у оптовика любой платёж даёт карточку), а лента компании без карточки — как шаг 4 `docs/DEMO.md` и e2e `payment.spec.ts`. Шаги: вход `user_cfo_nocard` (`U_235754`), «Всё верно», главный экран; затем «Платёж» с любым получателем.

Ожидается: виджет ленты явно пишет «Пока ничего важного для вашего бизнеса.» со ссылкой на профиль; платёж даёт карточку или «Ничего важного по этому действию» — но не пустую панель.

Плохо, если: пустой виджет без текста; карточка с натянутой связью в ленте; вечная загрузка.

### MC-06 · Форма платежа: сумма и панель
Шаги:
1. В поле суммы ввести `1e3`, `0x10`, `1,000`, `10.123`.
2. Ввести нормальную сумму, сменить получателя.

Ожидается: все четыре значения отвергаются; панель появляется через ~500 мс после ввода и не мигает на каждой цифре; смена получателя меняет панель; поле назначения растёт по тексту.

Плохо, если: форма принимает экспоненту, шестнадцатеричное число или три знака после запятой; панель перезапрашивается на каждое нажатие.

## Депозит и кредит

### MC-07 · Депозит и кредит: карточка с расчётом
Подготовка: вход `user_cfo_wholesale`. Шаги:
1. «Депозит» (`/deposits/new`): 50 000 000 на 6 месяцев, затем на 3 месяца.
2. «Кредиты» (`/loans`): «Новый транш», «Кредитная линия», 50 000 000, плавающая ставка.

Ожидается: у депозита тезис «Банк» по ставке от 11.09 (14% до конца года) и блок «Расчёт» с формулой и допущениями, сумма и срок в расчёте совпадают с формой; у кредита — `rate_burden` с отрицательным значением (банк ждёт снижения ставки); «Новый транш» переводит фокус на заголовок формы и прокручивает к ней; в трассе есть шаг `whatif.deposit_terms`.

Плохо, если: расчёт не совпадает с суммой или сроком; тезис банка не про ставку или с устаревшей датой; тезис ссылается на `calc:`, которого нет в карточке.

### MC-08 · Блок «Расчёт» на узких экранах и в тёмной теме
Шаги: `/showcase`, раздел «Карточка с расчётом» и панель compact — в светлой и тёмной теме ОС, на 320 px; депозит на ширине < 960 px и на телефоне.

Ожидается: на узком экране доход под формой, панель под ними; ничего не наезжает, горизонтального скролла нет.

Плохо, если: текст расчёта обрезан или выходит за карточку; в тёмной теме нечитаемый контраст.

## Карточка

### MC-09 · Качество текста карточки
Подготовка: любые 3–5 живых карточек (MC-03, MC-04, MC-07) или трассы регрессии из README. Шаги: прочитать каждую карточку целиком.

Ожидается: «что произошло» — событие из новости; «почему важно» связано с признаками именно этой компании; последствия и действия конкретные и звучат как предположения, а не гарантии; 1–2 тезиса в блоке, без повторов.

Плохо, если: пересказ новости без связи с компанией; общие советы, подходящие любой компании; тезис утверждает то, чего нет в источнике; один и тот же тезис в нескольких блоках.

### MC-10 · Цитата банка в карточке
Подготовка: карточка по ставке (MC-07 или кейс `page_key_rate_bank` из README). Шаги: найти блок «Как это оценивает банк», открыть источник.

Ожидается: тезис «Банк» дословно повторяет утверждение house view с датой, ссылка ведёт на отчёт банка; заменённые прогнозы не цитируются как текущие.

Плохо, если: пересказ вместо цитаты; цитата банка дважды (в обязательном блоке и в «Как это оценивает банк») при пометке «Карточка ждёт проверки» читается как ошибка; дата позиции устаревшая.

## Роли и followup

### MC-11 · Ракурс финдиректора и казначея в кейсах 12–14
Подготовка: `trace_id` из таблицы регрессии README; пары: ставка — кейсы 03 и 12 (`user_cfo_wholesale`), тарифы — 07 и 13 (`user_cfo_wholesale`), курс рубля — 06 и 14 (`user_cfo_autodealer`). Шаги: открыть `/trace/<trace_id>` обеих карточек пары рядом, сравнить «почему важно» и «действия».

Ожидается: у финдиректора — маржа, стоимость долга и финансирования, бюджет и план на год; у казначея — ликвидность, платёжный календарь, валютные позиции, размещение остатков, сроки и лимиты платежей; «что произошло» — то же событие из той же новости.

Плохо, если: тезисы отличаются только формулировкой, а по смыслу совпадают; у казначея акценты финдиректора или наоборот; разные события в «что произошло».

### MC-12 · Шаг 6 демо: смена роли на той же форме платежа
Шаги:
1. MC-04 за финдиректора — запомнить «почему важно» и «действия».
2. `/role` → «Казначей», снова та же форма, тот же получатель и сумма.

Ожидается: «почему важно» и «действия» в ракурсе казначея; «что произошло» и источники те же; пометки и ссылки на месте.

Плохо, если: та же карточка слово в слово (ответ из кэша без учёта роли); у одной из ролей «ничего важного».

### MC-13 · Followup: ответ на вопрос к карточке
UI для вопроса пока нет — проверка через API. Шаги:
1. Взять `card_id` карточки: из ответа `POST /interpret` или трассы кейса 03 (ставка) и 06 (курс) регрессии.
2. В Swagger под пользователем карточки `POST /interpret` с `action_context`: `{"type": "followup", "card_id": "<id>", "question": "Какую ставку банк ждёт на конец 2027 года?"}` (для кейса 06 — «Какой курс доллара банк ждёт на конец 2026 года?»), ещё вопрос «А если ЦБ снизит ставку в октябре?».

Ожидается: заголовок — короткий прямой ответ на вопрос; в «позиции банка» прогноз банка с датой (ставка — от 11.09, 12% на конец 2027); ответ за ~12 с, без таймаута.

Плохо, если: ответ пересказывает исходную карточку и не отвечает на вопрос; «что произошло» описывает сам вопрос вместо события; ссылка на источник, которого нет в карточке; `ModelUnavailable` по таймауту.

### MC-14 · Критик: противоречие позиции банка
Подготовка: трассы с вердиктами критика (кейсы регрессии или MC-04). Шаги: на экране трассы найти вердикты критика по кругам; при переписанном черновике сравнить его с замечаниями.

Ожидается: противоречие позиции банка без пометки «Расхождение» критик находит; согласный или уточняющий тезис и новое событие после прежнего факта противоречием не считает; переписанный черновик устраняет каждое замечание.

Плохо, если: критик спорит с фактом нового решения ЦБ; после второго круга замечание осталось, а карточка не помечена «ждёт проверки».

## Трасса и источники

### MC-15 · Экран трассы читается сверху вниз
Шаги: из карточки «Как получен вывод» → экран трассы; то же для трассы ленты главного экрана.

Ожидается: запрос и роль, время, токены, модели и рубли; шаги по-русски с аргументами и результатами (план, инструменты, черновик, вердикты критика по кругам, «Сборка карточки, круг N», итоговая карточка); читается без пояснений; в тёмной теме и на 390–1024 px ничего не наезжает.

Плохо, если: сырые ключи и JSON вместо подписей; шаги ленты (несколько карточек в одной трассе) перемешаны так, что не понять, к какой карточке шаг; трасса чужого пользователя открывается.

### MC-16 · Переход к источнику: PDF отчёта на нужной странице
Подготовка: PDF в `backend/data/raw`. Шаги: в карточке MC-04 — клик по источнику-новости и по источнику-отчёту, в т. ч. из «Итог» на экране трассы.

Ожидается: новость открывает статью; отчёт — PDF `/api/reports/<файл>#page=N` на странице с утверждением; без сессии ссылка отвечает 401.

Плохо, если: 404 при лежащем в `data/raw` файле; PDF открывается на первой странице; ссылка ведёт на чужой сайт.

### MC-17 · «Полезно / Не полезно»
Шаги: на карточке нажать «Полезно».

Ожидается: кнопка становится нажатой после ответа сервера (204), отзыв попадает в `useful_share` метрик (MC-20).

Плохо, если: кнопка не отмечается или отмечается до ответа при ошибке сервера.

## Живая новость и кэш

### MC-18 · Живая новость через API
Через API; экран вставки в приложении — MC-33. Шаги:
1. Под клиентом с кредитом (`user_cfo_wholesale`, `U_1941`) `POST /interpret` с `{"type": "page", "url": "https://example.com/news", "text": "<свежая новость о ставке>"}`.
2. Повторить тот же запрос.
3. Вставить длинный текст одной строкой.

Ожидается: карточка по новости с понятными факторами; повтор отвечает быстро, новая запись в `news` не появляется; заголовок в источниках карточки читаемый даже для текста одной строкой.

Плохо, если: повтор заново размечает новость; заголовок источника — весь текст новости; разметка факторов не про ставку.

### MC-33 · Живая новость в приложении
Шаги:
1. Войти за `user_cfo_wholesale` (`U_1941`), на главном экране в виджете ленты нажать «Вставить новость».
